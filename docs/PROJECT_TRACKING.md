## 1. Архитектура и реализованный стек

```
Browser (любая страница)
   │
   ▼
FastAPI Web Server (http://localhost:8000)
   ├── 1. Reverse Proxy Router
   │      ├── Проксирование контента www.ticketpro.by и auth.ticketpro.by
   │      ├── Санитизация кук (удаление domain=.ticketpro.by, замена SameSite=None -> SameSite=Lax)
   │      └── Инжекция плавающего HUD-виджета во все HTML-страницы
   │
   ├── 2. Bot Control REST API & SSE
   │      ├── POST /api/bot/start (запуск фоновой задачи снайпера)
   │      ├── POST /api/bot/stop (остановка снайпера)
   │      ├── GET  /api/bot/status (проверка состояния и количества забронированных мест)
   │      └── GET  /api/bot/stream (SSE-стрим живых событий и логов)
   │
   └── 3. Core Engine (Asyncio Producer-Consumer)
          ├── Fetcher: получение сессии, CSRF-токена и временного SVG схемы зала
          ├── Parser: regex-парсинг свободных мест (<g> и <circle>), фильтрация по ценам и секторам
          ├── Consumer Pool: конкурентный пул воркеров бронирования с защитой от овербукинга
          └── Continuous Loop: непрерывный цикл охоты до набора заданного числа билетов
```

## 2. Ключевые открытия по API Ticketpro (Technical Insights)

1. **Схема зала и билеты (SVG-эндпоинт)**:
   - Страница мероприятия делает запрос к `https://auth.ticketpro.by/ticket-api/v1/get-scheme-prices-grouped/{event_id}`.
   - Эндпоинт возвращает путь к временному SVG-файлу: `{"path": "https://auth.ticketpro.by/ticket/file/temp/<UUID>.SVG"}`.
   - SVG содержит все места зала:
     - Занятые места сгруппированы в `<g fill="#999999">`.
     - Свободные места сгруппированы по ценам `<g price_id="..."> <circle id="ticket_id" name="1:A/2:Sector/3:Row/4:Seat">`.
   - **Производительность**: скачивание SVG ~0.8s (при нормальной нагрузке), regex-парсинг 15 000 мест в памяти занимает всего ~7-8 мс.
2. **Ограничения инфраструктуры и протокола**:
   - Бэкенд работает на **HTTP/1.1** (HTTP/2 multiplexing не поддерживается).
   - Серверной фильтрации мест нет (всегда отдается полный SVG схемы зала).
   - Real-time модель: заголовки `no-cache`, поэтому условный кэш `ETag`/`304` не применяется.
3. **Бронирование места**:
   - `POST https://www.ticketpro.by/api/ticket/ticket-reserve/?ticket_id={ticket_id}&price_id={price_id}&count=1`
   - Требует сессионную куку `PHPBACKSESSID`, куку `_csrf-frontend` и заголовок `X-CSRF-Token`.
   - При успехе возвращает JSON корзины с таймером брони (`time_live: "09:59"` = 10 минут).
4. **Особенности работы браузерных кук (RFC 6265bis)**:
   - Ticketpro отдает `Set-Cookie: ...; domain=.ticketpro.by; SameSite=None; Secure`.
   - При проксировании на `http://localhost:8000` браузер отбрасывает куку без `Secure`, если указан `SameSite=None`.
   - **Решение**: Прокси-сервер очищает `domain` и подменяет `SameSite=None` на `SameSite=Lax`.

## 4. Бэклог идей и архитектурных планов (Roadmap & Ideas)

### 📌 Режимы работы снайпера (Core Strategy Modes)

#### 🚀 1. Быстрый режим (Fast Mode) — фокус на максимальной скорости:
- [ ] **Streaming Producer Pipeline (Потоковый парсинг без блокировок)**:
  - Связка «1 Фетчер + 1 Парсер» выступает как единая единица производителя (Producer Unit).
  - Парсер не собирает весь список мест в памяти целиком, а потоково отправляет каждый найденный подходящий билет напрямую в общую очередь консьюмеров в процессе разбора регулярных выражений.
  - Потребители (Consumers) начинают бронирование моментально при нахождении первого же свободного места, не дожидаясь окончания разбора всей схемы зала.
- [ ] **Shared Deduplicator (Защита от дублирования билетов)**:
  - Единое потокобезопасное хранилище просмотренных идентификаторов мест на уровне ядра бота.
  - Перед отправкой билета в очередь парсер сверяется с общим хранилищем: если место уже было отправлено другим производителем или предыдущей итерацией, оно отбрасывается.
- [ ] **Multi-Producer Support (Пул параллельных производителей)**:
  - Возможность конфигурации количества активных производителей (Producer Units) на одного бота.
  - Работа производителей со сдвигом по времени (Staggered Polling) для достижения непрерывного и более частого обновления данных о свободных местах.
- [ ] **In-Memory Anti-Contention (Устранение коллизий по местам)**:
  - Применение стратегий выборки мест в памяти (перемешивание порядка выдачи, выборка с конца списка) для исключения лобовой конкуренции за первые порядковые места с другими ботами.
- [ ] **Continuous Polling / Pipelining без искусственных пауз**:
  - Устранение жесткого таймаута между запросами: следующий запрос схемы уходит сразу по завершении предыдущего, удерживая темп на уровне естественного времени ответа сервера (~0.8s).

#### 🛋️ 2. Комфортный режим (Comfort Mode) — фокус на удобстве мест:
- [ ] **Поиск билетов рядом друг с другом (Co-located Seats)**:
  - Поиск соседних мест не по порядковому номеру билета, а по реальным координатам в SVG-схеме и атрибутам сектора, ряда и места.
- [ ] **Многоуровневые приоритеты (Priority Layers)**:
  - Пользовательские правила предпочтений (например: Сектор А приоритетнее Сектора Б; Ряды 3-7 приоритетнее Рядов 1-2).
